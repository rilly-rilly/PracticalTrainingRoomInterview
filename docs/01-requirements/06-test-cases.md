## 1. 测试范围与前置数据

### 1.1 测试范围与环境

| 项目 | 内容 |
| --- | --- |
| 被测系统 | 学生实训室进组选拔系统（Vue 3 + Spring Boot 3 + MySQL 8 课程作业） |
| 本轮被测版本 | `frontend` 可运行 mock 演示版（Vue 3.5 / Vite 5 / Axios 1.7） |
| 接口契约 | 前端 Axios 自定义 adapter 转发到 `frontend/src/mock/server.js`，接口路径、统一响应体 `{code,message,data}`、状态码与后端保持一致 |
| 演示数据 | `frontend/src/mock/seed.js`；浏览器本地存储键 `trainee-selection-demo-v2`（登录态键 `trainee-selection-auth-v1`） |
| 本轮覆盖 | 意向填报、导师评分与录取、名额控制、拟录取确认、递补与逾期、调剂补录、导入与账号、认证与权限、结果公示、页面五态反馈 |
| 本轮不覆盖 | 真实 MySQL 事务与并发压测、性能测试、渗透测试、跨浏览器兼容性专项、真实 BCrypt 算法本身（仅验证“库中无明文”原则） |

**执行约定**

1. 每条用例执行前，通过登录页「重置演示数据」或动态导入 `src/api/index.js` 调用 `authApi.resetDemo()` 恢复种子数据；重置后所有会话失效，需重新登录。用例中“DB”指 `localStorage['trainee-selection-demo-v2']` 中的数据。
2. 页面路径用例直接在浏览器操作；无法由页面触发的分支（如一次提交 4 个意向、请求体篡改名额）通过浏览器控制台动态导入 API 模块构造请求：`const { studentApi } = await import('/src/api/index.js')`。当前 mock 是 Axios adapter，**不要用裸 `fetch('/api/...')` 直连**，否则请求不会进入 mock。
3. 受保护接口需携带 `Authorization: Bearer <token>`；token 从登录响应或 `localStorage['trainee-selection-auth-v1']` 获取。
4. 状态名严格使用系统枚举：`待面试`、`面试完成`、`拟录取`、`递补`、`已确认`、`已放弃`、`已录取`、`未录取`。
5. 名额“已占用”只统计 `拟录取 + 已确认 + 已录取` 三种状态，`递补 / 未录取 / 已放弃 / 待面试 / 面试完成` 不占用名额。

## 4. 判定表

### 4.1 意向提交判定表

**条件定义**

| 条件 | 取值 | 说明 |
| --- | --- | --- |
| C1 窗口是否开放 | Y / N | `windowOf(db,'intent').isOpen` |
| C2 意向数量 | 0 / 1~3 / ≥4 | 按 `choices.length` 判定 |
| C3 简介是否有效 | Y / N | `trim` 后 ≥20 字 |
| C4 本轮是否已提交 | Y / N | 是否存在 `studentId + round=1` 的记录 |

**规则表**（`—` 表示不关心）

| 规则 | C1 窗口 | C2 数量 | C3 简介 | C4 重复提交 | 动作 / 预期 |
| --- | --- | --- | --- | --- | --- |
| R1 | N | — | — | — | 410「意向填报时间窗口已关闭，当前不可提交（410）」 |
| R2 | Y | 0 | — | — | 422「请至少选择 1 个意向导师」 |
| R3 | Y | ≥4 | — | — | 422「最多填报 3 个平行意向，当前提交了 N 个」 |
| R4 | Y | 1~3 | N | — | 422「个人简介不能为空且不少于 20 字」 |
| R5 | Y | 1~3 | Y | Y | 422「本轮意向已提交，不可重复填报」 |
| R6 | Y | 1~3 | Y | N | 200「意向提交成功」，新增 N 条 `待面试 / round=1 / priority=1..N` |

**同条件补充规则**（服务端在 R2/R3 之后、R4 之前校验导师集合）

| 补充规则 | 条件 | 动作 / 预期 |
| --- | --- | --- |
| S1 | C1=Y，C2=1~3，所选导师存在重复 | 422「同一导师不能重复填报」 |
| S2 | C1=Y，C2=1~3，所选导师 ID 不存在 | 400「所选导师不存在：<id>」 |

> 判定顺序：C1 → C2（0、≥4）→ 导师去重/存在性 → C3 → C4 → 成功。先命中先生效，后续条件不再校验。

### 4.2 导师录取判定表（decision=`admit`）

**条件定义**

| 条件 | 取值 | 说明 |
| --- | --- | --- |
| C1 是否本人报考 | Y / N | `intention.teacherId === 当前导师 id` |
| C2 当前状态 | 待面试 / 面试完成 / 其他 | 其他含 `拟录取、递补、已确认、已放弃、已录取、未录取` |
| C3 名额是否已满 | Y / N | 仅录取分支校验：`roomUsed(exclude 本 id) ≥ room.quota` |

**规则表**

| 规则 | C1 本人报考 | C2 状态 | C3 名额已满 | 动作 / 预期 |
| --- | --- | --- | --- | --- |
| R1 | N | — | — | 403「只能决定报考本人的学生」 |
| R2 | Y | 待面试 | — | 422「只有「面试完成」状态可以决定是否录取，当前为「待面试」」 |
| R3 | Y | 其他 | — | 422「只有「面试完成」状态可以决定是否录取，当前为「其他状态名」」 |
| R4 | Y | 面试完成 | Y | 409「名额已满：<实训室> 招收上限 N 人，当前已占用 N 人（409）」，状态保持「面试完成」 |
| R5 | Y | 面试完成 | N | 200 置「拟录取」；该生拟录取数为 1 → 自动转「已确认」并写 `mode=auto`；≥2 → 保持「拟录取」待学生选择 |

**补充说明**

1. `decision` 不在 `admit / waitlist / reject` 内时，在 C1、C2 校验通过后返回 400「录取决定参数不合法」。
2. `waitlist` 与 `reject` 不校验 C3；`waitlist` 顺位按同实训室现有 `递补` 的最大 `rank + 1` 计算，返回「已加入递补名单，顺位 N」。
3. `reject` 返回「已标记为未录取，学生将进入调剂流程」。

## 6. 判定表规则合并说明与测试结论模板

### 6.1 规则合并说明

1. **原始组合数**：意向提交判定表原始组合为 `2（窗口）× 3（数量）× 2（简介）× 2（重复）= 24` 种；导师录取为 `2（本人报考）× 3（状态）× 2（名额）= 12` 种。
2. **合并方法**：对输出结果相同且仅个别条件取值不同的组合，用 `—`（不关心）合并。例如“窗口关闭”时，无论数量、简介、重复提交取何值，结果都是 410，24 种组合中 12 种合并为 R1；“数量为 0”时 2 种合并为 R2；“数量 ≥4”时 2 种合并为 R3；“1~3 且简介无效”时 2 种合并为 R4；“1~3、简介有效、已提交”2 种合并为 R5；“1~3、简介有效、未提交”2 种合并为 R6。导师录取同理，R1 合并 6 种、R2 合并 2 种、R3 合并 2 种、R4 合并 1 种、R5 合并 1 种。
3. **优先级与冲突**：合并后的规则按服务端实际校验顺序排序（窗口 → 数量 → 导师集合 → 简介 → 重复提交 → 成功；本人报考 → 状态 → 决定参数 → 名额）。冲突时以先命中的规则为准，后置条件不再求值，因此 R1 优先于所有输入校验，R2/R3 优先于简介与重复提交。
4. **等价类映射**：每个等价类至少被一条规则或一条补充规则覆盖；每个边界值至少出现在一条用例的输入或前置中。建议覆盖率按 `已覆盖规则数 / 合并后规则总数` 统计，意向提交为 6 条主规则 + 2 条补充规则，导师录取为 5 条主规则 + 3 条补充说明。
5. **结论口径**：只要任一规则的实际输出（状态码、message、状态、名额、落库）与预期不一致，即记为失败；同一规则的多条用例按最严重结果汇总，不重复计缺陷。
